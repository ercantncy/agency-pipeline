# Looker Studio setup: the production path

The repository runs locally on DuckDB with synthetic data and renders self-contained HTML reports. In production, the same dbt project targets BigQuery and the client-facing layer is a white-label Looker Studio report. This guide covers that path.

Anything marked **verify** depends on Google's current UI or pricing and should be checked before you quote it to a client.

## What the repository gives you and what you add

Provided by the repository:
- The dbt project (`dbt/`) with staging models and marts (`fct_paid_daily`, `fct_web_daily`, `fct_paid_vs_ga4_reconciliation`, `fct_seo_daily`, `fct_seo_query_monthly`, `rpt_client_monthly`, `dim_client`).
- A `prod` dbt target using `dbt-bigquery`. It is not exercised in CI.
- Synthetic extractors that write to DuckDB.

You add per engagement:
- Real extraction from client sources into BigQuery `raw` tables with the same column shapes as the spec (Google Ads API, Meta Marketing API, GA4 Data API, Search Console). The synthetic extractors in `sources/synthetic/` show the target shapes; real extractors or a connector must produce them. The repository's `load.py` targets DuckDB, so a BigQuery loader is a per-engagement piece of work.
- The Looker Studio report itself, which is built in the Looker Studio UI and is not generated by the repository.

## 1. BigQuery project and datasets

1. Create a Google Cloud project owned by the agency (so the agency owns the data). Enable billing; the free tier still requires a billing account (**verify**).
2. Pick a region once and keep every dataset in it. Looker Studio, BigQuery and dbt all need datasets co-located. Use `US` or `EU`/`europe-west2` (London) depending on where the agency's clients are (**verify** current location availability). Region cannot be changed later without copying data.
3. Dataset layout. Two sensible patterns:
   - **One set of datasets per agency** (recommended for a single-agency deployment): `raw`, `staging`, `marts`. All clients live in the same tables, separated by the `client_id` column, exactly as the dbt models are written.
   - **One project per agency** if you serve several agencies: keep each agency fully isolated in its own project, with the same three datasets inside.
   Do not create a dataset per end client. The models assume `client_id` as a column, and separate datasets would multiply models and permissions without benefit.

## 2. Service account and dbt target

1. Create a service account, for example `dbt-runner@<project>.iam.gserviceaccount.com`.
2. Grant the minimum roles: `BigQuery Data Editor` on the `raw`, `staging` and `marts` datasets, and `BigQuery Job User` on the project. Avoid project-wide Owner/Editor.
3. Create a key (JSON) only if you must run dbt outside Google Cloud; prefer workload identity or short-lived credentials where possible (**verify** for your runner). Store keys in a secrets manager or CI secrets, never in the repo.
4. Configure the `prod` output in `dbt/profiles.yml` with `type: bigquery`, `method: service-account` (or `oauth` locally), `project`, `dataset` (as the base dataset), `location` (your chosen region), and `threads`. Read secrets from environment variables. The exact keys the repository's profile expects should be checked against `dbt/profiles.yml` (**verify** after pulling the current version).
5. Run: `dbt build --target prod` from the `dbt/` directory. Confirm the six marts tables exist in the `marts` dataset and tests pass.
6. Schedule it (Cloud Scheduler plus Cloud Run job, GitHub Actions on a cron, or similar) after extraction, then run the monitoring check and send alerts on a non-zero exit code.

## 3. Connect Looker Studio to the marts

1. In Looker Studio, create a data source with the BigQuery connector. Choose the project, the `marts` dataset, and one table.
2. Create one data source per marts table you need:
   - `rpt_client_monthly` for the summary and paid overview pages.
   - `fct_paid_daily` for trends and campaign tables (filter by channel for Google Ads and Meta Ads pages).
   - `fct_web_daily` for the website page.
   - `fct_seo_daily` and `fct_seo_query_monthly` for the SEO page.
   - `fct_paid_vs_ga4_reconciliation` for the data quality page.
   - `dim_client` for client names and filter options.
3. Set data source credentials to **Owner's credentials** so report viewers do not need BigQuery access. The owner (or a dedicated service identity) must have read on the datasets. Service-account-based data source credentials are available in Looker Studio (**verify** current setup steps).
4. Use the custom-query option sparingly. Pointing at tables keeps queries predictable and cheaper.
5. Add calculated fields only where necessary (for example formatted deltas). Prefer computing metrics in dbt.

## 4. The 7-page template

Build one report with seven pages that mirror the sections of the HTML report in the specification:

| Page | Content | Primary data source |
|---|---|---|
| 1. Executive summary | KPI tiles (spend, conversions, CPA, ROAS) with month-over-month deltas; commentary text box | `rpt_client_monthly` (channel = total_paid) |
| 2. Paid overview | Spend, conversions, CPA, ROAS trends by channel | `rpt_client_monthly`, `fct_paid_daily` |
| 3. Google Ads campaigns | Campaign table: spend, clicks, conversions, CPA | `fct_paid_daily` (channel = google_ads) |
| 4. Meta Ads campaigns | Campaign table, same metrics | `fct_paid_daily` (channel = meta_ads) |
| 5. Website | Sessions, engaged sessions, key events and revenue by channel group | `fct_web_daily` |
| 6. SEO | Top queries table, clicks/impressions and position trend | `fct_seo_query_monthly`, `fct_seo_daily` |
| 7. Data quality | Session-to-click ratio chart per channel, current status, plain-English note | `fct_paid_vs_ga4_reconciliation` |

Tips:
- Put a report-level `client_id` control at the top of each page (see section 6) and a date range control.
- Use month over month fields from `rpt_client_monthly` rather than computing in the report.
- Commentary: paste the reviewed monthly commentary into a text box each month, or store it in a small table and chart it from a data source if you want it automated (that table is not part of the current marts; it would be an addition).
- Keep visuals plain. Fewer, clearer charts survive client scrutiny.

## 5. White-labeling

- **Theme.** Report > Theme and layout > Customize theme. Set the primary color (the repo's synthetic agency uses `#2F6FEB`), fonts and background. Save as a custom theme and reuse it across the agency's reports.
- **Logo.** Insert the agency logo as an image on the header of each page (or in the report layout so it repeats). Do not show Google or vendor logos you do not need.
- **Report title and sharing text.** Name the report in the agency's brand, not the pipeline's.
- **Custom domain.** Looker Studio does not offer a custom domain on shared report links (**verify**). Clients will see a lookerstudio.google.com URL. Sending the report as a scheduled PDF email avoids this.
- **Scheduled delivery.** Looker Studio can email scheduled PDF delivery (**verify** limits). For a fully branded email, send it from the agency's own system.

## 6. One report for many clients: the two approaches

**A. Single report with a client_id filter.**
- Add a drop-down control on `client_id`. For client-facing links, use a URL parameter or a per-client default filter so each client sees only their data (**verify** the current options for locking a filter; a drop-down alone does not stop a viewer from changing it).
- Advantage: one template to maintain.
- Risk: if the filter is not enforced, a viewer may see other clients' data. Do not use this for client-facing links unless you have confirmed the data cannot be exposed.

**B. Per-client copies (recommended for client-facing access).**
1. Build and finish the master template.
2. Copy the report for each client (Make a copy). When prompted, keep the same data sources.
3. In each copy, add a report-level filter on `client_id` equal to that client, and make sure the filter is applied to every page and every data source used. Lock editing for viewers (viewers cannot edit the filters of a report they only have view access to).
4. Name the report for the client and share the copy with that client.
5. Keep a checklist of copies. When you change the template, you must apply the change to every copy (this is the main maintenance cost and the main reason for the retainer).

For stronger isolation, use a data source with a parameter or a custom query that filters by client at the BigQuery level (**verify** the parameter feature set). Alternatively use an authorized view per client in BigQuery, with a separate data source per client, so the data itself cannot leak.

## 7. Sharing and permissions

- Share each client report with the client's email addresses as Viewer, or with a link restricted to specific people. Avoid "anyone with the link" for client data.
- Keep editors to the agency and you.
- With owner's credentials, viewers do not need BigQuery access. Make sure the owner is a stable account (a role account, not a person who may leave), or the report breaks when it is removed.
- Review sharing quarterly. Remove ex-employees and ex-clients.
- The data source is the sensitive piece: anyone who can edit the report can see data from the whole data source. Do not give clients editor access.

## 8. Costs

| Item | Cost | Notes |
|---|---|---|
| BigQuery storage | First 10 GiB per month free | (**verify**) Small-agency volumes (a few clients, daily rows) are far below this |
| BigQuery queries | First 1 TiB per month free | (**verify**) Querying aggregated marts tables from Looker Studio uses little; avoid querying raw tables from the report |
| Looker Studio | Free | Standard reports and connectors are free |
| Looker Studio Pro | Per user per month | Needed for team workspaces, support and some admin features. Pricing is around $9 per user per month at the time of writing (**verify**) |
| Paid connectors (if used) | Varies | Passed through at cost, quoted during scoping |
| Orchestration | Free to low | Free with GitHub Actions at small scale; Cloud Run/Scheduler is pennies. (**verify** for your volume) |

Control query cost: cache is on by default in Looker Studio, keep date ranges bounded, and consider partitioning the marts by date and clustering by `client_id` if tables grow (this is an optimisation not in the current dbt models).

## 9. Handover checklist

- BigQuery project and datasets owned by the agency; roles reviewed.
- Service account created, keys in a secrets manager, rotation noted.
- `dbt build --target prod` passing and scheduled; monitoring alerts routed.
- Master report plus one copy per client, filters verified by opening each copy as a test viewer.
- Theme and logo applied; sharing reviewed.
- Loom handover recorded; written handover document delivered.
